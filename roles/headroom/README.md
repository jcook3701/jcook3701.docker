# Headroom

[Headroom](https://github.com/headroomlabs-ai/headroom) compresses tool output,
logs, files, RAG content, and conversation history before they reach an LLM.
The `jcook3701.docker.headroom` role deploys its persistent HTTP proxy in a
restricted Docker container through the collection's established
`jcook3701.utils.container_engine` lifecycle integration.

This role deliberately manages the proxy only. It does not install Headroom's
host wrapper, modify Codex or Claude configuration, or deploy the optional
Qdrant and Neo4j memory stack.

## Requirements

- Docker Engine and Docker Compose v2 on the target host.
- The `jcook3701.utils.container_engine` role and `community.docker` collection.
- Network access to GHCR for the pinned image on first deployment.
- Network access from the proxy to the LLM providers used by its clients.

The role does not install or reconfigure Docker.

## Security model

Headroom is a local man-in-the-middle proxy. It receives prompts, source code,
tool results, provider credentials, and responses in plaintext before forwarding
traffic to the configured provider over TLS. Persistent CCR data, operational
logs, settings, and savings information are stored unencrypted under
`/opt/headroom/data` by default.

The default host binding is `127.0.0.1:8787`. The role refuses any non-loopback
binding unless `headroom_proxy_token` is nonempty. Store that value in Ansible
Vault and use a strong random token, for example one generated by
`openssl rand -hex 32`. Remote clients should send it in the
`X-Headroom-Proxy-Token` header.

Because the proxy must listen on `0.0.0.0` inside its network namespace for
Docker port forwarding, Headroom logs an unauthenticated-bind warning for the
default deployment. The published host port remains restricted to loopback.

The token and any values in `headroom_extra_environment` are written to the
root-only Compose file and are visible to Docker administrators through
container inspection. Prefer forwarding provider credentials from each client
instead of storing them in the proxy environment when the provider protocol
supports that model.

The anonymous Headroom upload beacon is disabled by default. The proxy retains
outbound provider access and uses a normal Docker bridge network. Apply host or
network egress controls if stricter destination restrictions are required.

## Data lifecycle

- `present`: create private persistent storage, render Compose configuration,
  and deploy the proxy.
- `absent`: stop and remove the container while preserving configuration,
  state, caches, and the image.
- `teardown`: stop the stack and remove the Compose file while preserving
  `/opt/headroom/data` by default.
- `headroom_teardown_remove_images: true`: explicitly ask the shared engine
  role to remove the stack image during teardown.
- `headroom_teardown_remove_data: true`: permanently remove the entire
  `headroom_base_dir`, including CCR originals, memories, logs, settings, and
  savings history.

Back up persistent data before enabling the destructive teardown option.

When changing `headroom_image`, verify the image runtime UID/GID and update
`headroom_container_uid` and `headroom_container_gid` together. The default tag
is immutable by version but can be pinned further to a tested digest.

## Example playbook

```yaml
---
- name: Deploy Headroom
  hosts: "headroom_hosts"
  become: true
  roles:
    - role: "jcook3701.docker.headroom"
      vars:
        headroom_state: "present"
```

For intentional LAN access, provide a Vault-encrypted token and explicit bind:

```yaml
headroom_bind_ip: "0.0.0.0"
headroom_proxy_token: "{{ vault_headroom_proxy_token }}"
```

## Client configuration and verification

After deployment, verify readiness locally:

```bash
curl --fail --silent http://127.0.0.1:8787/readyz
sudo docker compose -f /opt/headroom/compose.yml ps
```

OpenAI-compatible clients normally use `http://127.0.0.1:8787/v1` as their
base URL. Anthropic-compatible clients use `http://127.0.0.1:8787`. Configure
the individual client to forward its provider credential and, for a remotely
published proxy, the separate `X-Headroom-Proxy-Token` header.

The `/dashboard` endpoint displays local savings information. Headroom's
loopback-gated administrative surfaces are not automatically opened to remote
clients merely by publishing the proxy port.
